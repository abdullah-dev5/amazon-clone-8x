Pay particular attention to:

* Order placement
* Coupon application if it creates persistent state
* Order cancellation
* Cart mutations
* Address changes
* Wishlist mutations
* Authentication/signup operations

Use the simplest appropriate mechanism.

Prefer:

* Unique database constraints
* Transactions
* Idempotency keys where appropriate
* Atomic database operations

Do NOT introduce Redis merely to implement idempotency.

---

## 4. DATABASE INTEGRITY

Database constraints should protect important invariants rather than relying exclusively on application code.

Review whether important relationships need:

* Unique constraints
* Foreign keys
* Appropriate indexes
* Non-null constraints
* Valid status representations
* Transaction boundaries

Examples:

* A user's email should be unique.
* An order item must reference a valid product/order.
* A coupon code should be uniquely identifiable.
* A user should not accidentally have multiple default addresses if the model requires one.
* An order must not be created without valid order items.

Do not add constraints that create unnecessary complexity for this application.

---

## 5. TRANSACTIONS

Use transactions when multiple database changes must succeed or fail together.

Examples:

Order placement may involve:

1. Validate cart
2. Re-check stock
3. Calculate authoritative pricing
4. Apply valid discount
5. Decrement stock
6. Create order
7. Create order items
8. Clear cart

These should not leave the database half-updated if something fails.

Likewise, order cancellation should preserve stock/order consistency if stock restoration is part of the business rule.

Do not wrap every database query in a transaction unnecessarily.

Use transactions around actual atomic business operations.

---

## 6. CONCURRENCY

Do not assume users only click once or requests arrive sequentially.

Consider:

* Two checkout requests arriving simultaneously
* Two cart updates arriving close together
* Stock changing between cart display and checkout
* Two cancellation requests
* Coupon validation followed by changed cart contents
* Multiple requests updating the same user-owned resource

The database/server must protect business invariants.

Do not solve every concurrency problem with locks or infrastructure.

Use the simplest correct approach available in the current database.

---

## 7. AUTHORIZATION / OWNERSHIP

Authentication answers:

> "Who is this user?"

Authorization answers:

> "Is this user allowed to perform this operation?"

Every user-owned resource must be checked server-side.

Especially:

* Orders
* Addresses
* Wishlist
* Cart
* Account data

Never trust an ID supplied by the browser merely because the user is logged in.

For example:

`GET /orders/123`

must verify that order `123` belongs to the current user.

This should be enforced at the server/data-access layer, not only by hiding links in the UI.

---

## 8. INPUT VALIDATION

Validate all external input at the server boundary.

Review:

* Query parameters
* Route parameters
* Form data
* IDs
* Quantities
* Coupon codes
* Search terms
* Status values
* Pagination/sorting values

Reject:

* Invalid types
* Invalid ranges
* Empty required values
* Impossible enum/status values
* Malformed IDs
* Unexpected input

Keep validation proportional to the application.

If existing manual validation is adequate, do not introduce a validation library purely for the sake of having one.

If repeated validation is becoming error-prone, consider a small schema-based approach.

---

## 9. PRICING / MONEY

Treat pricing as business-critical.

Never trust:

* Product price from the browser
* Cart subtotal from the browser
* Discount amount from the browser
* Final total from the browser

The server should calculate:

`subtotal`

→ `discount`

→ `shipping`

→ `tax` if the application supports it

→ `final total`

Use appropriate numeric handling for money.

Do not use floating-point arithmetic carelessly for monetary calculations.

Keep the calculation logic centralized so different parts of checkout do not calculate different totals.

---

## 10. COUPON SAFETY

Coupon logic must be server-authoritative.

Check:

* Code exists
* Active/inactive state
* Expiration
* Minimum subtotal
* Discount type
* Discount amount
* Maximum discount where applicable
* Discount cannot make the order negative

The browser may request:

`SAVE10`

but the server determines what `SAVE10` actually means.

Do not trust a client-supplied:

`discount = 10`

---

## 11. ORDER STATE MACHINE

Order statuses should represent valid states.

Do not allow arbitrary status strings to be written from the browser.

Define valid states and sensible transitions.

For example:

`PLACED → PROCESSING → SHIPPED → DELIVERED`

and where appropriate:

`PLACED → CANCELLED`

Do not allow nonsensical transitions such as:

`DELIVERED → PROCESSING`

unless there is an explicit business reason.

If status changes are currently demo-controlled, keep that mechanism simple and clearly server-side.

---

## 12. ERROR HANDLING

Errors should be handled intentionally.

For API/server operations:

* Return appropriate status codes
* Return safe user-facing messages
* Log useful server-side information where appropriate
* Do not expose stack traces or internal database errors to users

For the UI:

* Show meaningful error feedback
* Preserve user input where possible
* Avoid silently failing
* Avoid leaving optimistic UI in an incorrect state
* Provide retry/recovery where useful

Do not create a massive global error-handling framework unless the current architecture actually needs it.

---

## 13. LOADING / EMPTY / ERROR STATES

Every new user-facing feature should consider:

### Loading

What does the user see while data is being loaded?

### Empty

What happens when there is nothing to display?

### Error

What happens when the request fails?

### Success

How does the user know their action succeeded?

Examples:

* No recently viewed products
* No recent searches
* No recommendations
* Invalid coupon
* Expired coupon
* Failed coupon request
* No order history
* Unknown order status

Do not leave blank sections or broken layouts.

---

## 14. RACE CONDITIONS IN UI

Avoid UI bugs caused by asynchronous operations.

Watch for:

* Stale requests overwriting newer results
* Search results from an older query appearing after a newer query
* Double submissions
* Optimistic updates without rollback
* Component unmount during async work
* Multiple coupon applications racing
* Cart updates arriving out of order

Do not add complicated state-management infrastructure unless necessary.

---

## 15. NEXT.JS / REACT DISCIPLINE

Follow the existing Next.js App Router architecture.

Prefer Server Components when interactivity is not required.

Use Client Components only where browser interaction/state is actually needed.

Avoid:

* Unnecessary `useEffect`
* Fetching server data into client state without reason
* Duplicate server/client sources of truth
* Excessive context
* Excessive global state
* Prop drilling that can be avoided naturally
* Components that become unnecessarily large
* Re-rendering large sections because of tiny state changes

Do not optimize React code based on theoretical performance.

Fix actual architectural problems and obvious unnecessary work.

## 16. URL / SEARCH STATE

For example:

* Search query

* Price filter
* Sort

This makes pages:

* Shareable

* Browser-navigation friendly

Do not force every piece of UI state into the URL.

Only state that represents the current navigable view belongs there.

## 25. DATA MIGRATION DISCIPLINE

3. Minimize schema changes.
4. Consider existing data.
5. Ensure seed data remains valid.
6. Test the application after migration.

Do not redesign the database simply because a theoretical production system might use a different schema.
