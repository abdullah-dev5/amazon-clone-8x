**Schema**: minimal `Coupon` model (code, type `PERCENT`/`FIXED`, value,

- Risk: every real order a real signed-in user places will claim "Delivered" to them in 2 days, permanently, regardless of anything actually happening. - Recommendation: smallest real fix — add `PROCESSING` to the `OrderStatus` enum (with a CHECK constraint, same technique already used for `CANCELLED`), and a tiny internal-only transition mechanism: either (a) a deterministic transition computed and *written* the first time an order is read past each threshold (so it's a real row, not a re-derived guess, but still needs no cron), or (b) a minimal authenticated-demo-only `POST /api/orders/:id/advance` for manually walking an order forward, gated to the order's own owner or dropped entirely if a cron/background job is out of scope (it is, per the scope rule).
